# 分かったこと

## 1. 機能・情報設計の目的

機能・情報設計は、ユーザー調査後に分かったことをもとに、サイトが「何をできるようにするか」と「何を、どのまとまりで伝えるか」を決める工程である。

見た目を作る前に、次の内容を整理する。

- ユーザーが達成したい目的
- ユーザーが必要とする情報
- 目的達成のために必要な機能
- 情報をどのページ・セクションに配置するか
- どの情報や機能を優先するか

## 2. ユーザー調査後の進め方

### Step 1：調査結果を要件として整理する

インタビューや観察で出てきた発言を、単なる感想ではなく、次の形に変換する。

| 整理するもの | 内容 | ポートフォリオの例 |
| --- | --- | --- |
| ユーザーの目的 | 何を達成したいか | 制作者の実力や考え方を短時間で知りたい |
| 困りごと | 何が分からない・不安か | 制作物だけでは担当範囲や成果が分からない |
| 必要な情報 | 判断に必要な材料は何か | 背景、課題、役割、工夫、成果、使用技術 |
| 成功状態 | 何ができれば目的達成か | 詳細を確認し、問い合わせや応募へ進める |

調査結果から直接「機能を追加する」と決めず、まずユーザーの目的・課題・必要情報を分ける。

### Step 2：必要な機能を洗い出す

目的と課題を満たすために必要な行動を考え、機能に変換する。ポートフォリオでは、機能が多いことよりも、閲覧者が迷わず判断できることを重視する。

| ユーザーの行動 | 必要になりうる機能 |
| --- | --- |
| 制作物を一覧から探す | 作品一覧、カテゴリ分け、タグ、絞り込み |
| 作品の詳細を理解する | 作品詳細ページ、画像拡大、制作概要 |
| 制作者の役割を知る | 担当範囲・制作プロセスの表示 |
| 次の作品へ移動する | 前後の作品へのリンク、関連作品 |
| 制作者へ連絡する | 問い合わせフォーム、メールリンク、SNSリンク |
| 迷わず移動する | グローバルナビ、パンくず、ページ内目次 |

必要性が調査で確認できていない機能は、「必要」と断定せず仮説として扱う。

### Step 3：掲載情報を決める

掲載情報は、ユーザーが目的を達成するための判断材料として整理する。ポートフォリオの作品ページなら、次のような構成が考えられる。

1. 作品名・概要
2. 制作した背景や依頼の目的
3. 解決したい課題
4. 想定ユーザー
5. 自分の担当範囲
6. 制作プロセス・判断の流れ
7. 工夫した点とその理由
8. 成果・結果・学び
9. 使用ツールや技術
10. 関連作品や問い合わせへの導線

すべてを載せるのではなく、「閲覧者が何を判断するために必要か」という基準で残す。

### Step 4：サイトマップにまとめる

情報をページ単位の階層に整理する。サイトマップは、ページ同士の関係と、情報の置き場所を確認するための成果物である。

例：

```text
トップページ
├─ About（自己紹介・スキル・経歴）
├─ Works（制作実績一覧）
│  ├─ 作品A 詳細
│  ├─ 作品B 詳細
│  └─ 作品C 詳細
├─ Process（制作姿勢・進め方）
└─ Contact（問い合わせ）
```

作品数が少ない場合は、独立ページを増やさずトップページ内のセクションにまとめる案もある。ページを増やすこと自体を目的にしない。

### Step 5：優先順位を決める

情報や機能を、ユーザー価値と制作上の重要度で並べ替える。最初から全部を実装するのではなく、まず目的達成に不可欠な範囲を決める。

| 優先度 | 判断の目安 | 例 |
| --- | --- | --- |
| Must | ないとサイトの目的を達成できない | 作品の概要、担当範囲、問い合わせ導線 |
| Should | あると理解・比較しやすい | 制作プロセス、成果、関連作品 |
| Could | 余力があれば追加する | 高度な絞り込み、アニメーション |
| Won't now | 今回は扱わない | 根拠のない会員機能、過剰な管理機能 |

優先順位には、ユーザー調査で得た根拠や仮説を添える。

## 3. ポートフォリオ向けの具体例

### 例：閲覧者が作品の見た目だけでなく、考え方も知りたい場合

**課題**：作品画像だけでは、なぜそのデザインにしたのか、どこまで自分が担当したのかが伝わらない。

**必要な情報**：課題、役割、判断理由、制作プロセス、成果。

**必要な機能**：作品詳細へ移動する導線、ページ内目次、関連作品へのリンク。

**サイト構成**：作品一覧 → 作品詳細 → 問い合わせ、という流れを基本にする。

**優先順位**：作品詳細の内容と問い合わせ導線をMust、アニメーションや高度な検索をCouldとする。

このように、調査結果 → ユーザーの目的 → 必要情報・機能 → ページ構成 → 優先順位の順に整理すると、判断のつながりを説明できる。

## 5. 完了基準

次の状態になれば、機能・情報設計はいったん完了とする。

- サイトの目的と主要ユーザーの目的が短く説明できる
- 調査結果から導いた要件と、まだ仮説のものを区別できる
- 必要な機能と、今回は扱わない機能が一覧になっている
- 各ページに何を掲載するか決まっている
- サイトマップでページの関係が説明できる
- Must / Should / Could などで優先順位が付いている
- 各判断に理由または根拠がある
- 次のユーザーフローで、ユーザーが目的達成までに取る行動を確認できる
- ワイヤーフレームに渡せる情報量・ページ構成になっている

## 6. ユーザーフロー・ワイヤーフレームとの違い

| 工程 | 主に決めること | ポートフォリオでの問い |
| --- | --- | --- |
| 機能・情報設計 | 何が必要か、何を載せるか、どのページに置くか | 作品詳細には何を載せ、どの機能が必要か |
| ユーザーフロー | ユーザーが目的達成までにどう進むか | 作品一覧から詳細を見て問い合わせるまで、どんな順番で進むか |
| ワイヤーフレーム | 情報を画面上にどう配置するか | 作品詳細で、概要・課題・成果をどの位置に置くか |

順番のイメージは、次のとおり。

```text
調査結果
  ↓
要件・必要機能・掲載情報の整理
  ↓
サイトマップ・優先順位
  ↓
ユーザーフロー
  ↓
ワイヤーフレーム
  ↓
ビジュアルデザイン・実装
```

機能・情報設計は「画面をどう見せるか」より前に、「何を提供するか」を決める工程である。ユーザーフローは行動の順序、ワイヤーフレームは画面内の配置を扱う。
