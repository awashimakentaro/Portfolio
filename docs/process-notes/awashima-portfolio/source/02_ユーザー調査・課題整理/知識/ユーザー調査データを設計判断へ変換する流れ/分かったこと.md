# 分かったこと

## 結論はグラフから直接出すものではない

調査結果は、次の順番で解釈する。

1. 回答データを事実として整理する
2. 選択数・割合・平均値を集計する
3. 自由記述を似たテーマに分類する
4. 複数の回答に共通する傾向を確認する
5. ユーザーに起きる問題として文章化する
6. 影響と改善コストで優先順位を決める
7. 機能・情報設計の要件へ変換する
8. プロトタイプや再調査で仮説を検証する

つまり、調査結果は「数値」から「発見」へ、発見から「課題」へ、課題から「設計判断」へ変換していく。

## 今回の調査で実際に行った変換

### 1. まず判断したいことを決めた

今回の調査で判断したいことは、主に次の内容だった。

- 最初の画面で何を伝えるべきか
- 作品ページに何の情報を載せるべきか
- 採用担当者が評価しやすい情報は何か
- どの課題から改善するべきか

### 2. 回答を数値化した

回答は3件だった。なお、そのうち1件はUI/UXデザイナー兼採用担当という仮想ペルソナによる合成回答であり、実際の回答者の調査結果とは分けて扱う必要がある。

今回確認した主な数値は次の通り。

| 分析項目 | 結果 |
| --- | --- |
| 最初に確認する情報 | 代表的な制作物・プロジェクトが2件、成果や実績が1件 |
| 情報の見やすさ | 平均4.0 |
| 制作背景・課題設定 | 平均3.7 |
| 成果・効果 | 平均5.0 |
| プロセス・改善内容 | 平均4.3 |
| 実績の具体性 | 平均4.7 |
| 最初の画面で何をしている人か分かりにくい | 3件中3件 |
| 読みやすさ・ナビゲーションに関する問題 | 3件中2件 |

ここで分かるのは、「何が重要だと回答されたか」と「どの問題が複数の回答に現れたか」である。平均値だけを見て結論を出さず、選択数と自由記述も合わせて見る。

### 3. 自由記述をテーマに分類した

自由記述から、次のようなテーマを抽出した。

- ポジションや何ができる人か分からない
- 本人の担当範囲が分からない
- 成果や効果が分からない
- 文章量や情報量が多い
- アニメーションによって閲覧が遅くなる可能性がある
- 成果物、GitHub、デモなどへの直接リンクが欲しい

自由記述は一つずつの感想として扱うのではなく、同じ意味の回答をまとめる。この作業はアフィニティダイアグラム、またはアフィニティマッピングに近い。

### 4. 事実と解釈を分けた

結論を説明するときは、次の3段階を分ける。

| 段階 | 今回の例 |
| --- | --- |
| 事実 | 3件中3件が「最初の画面で何をしている人か分かりにくい」を選択した |
| 解釈 | ファーストビューだけでは、役割や強みが短時間で伝わっていない可能性がある |
| 設計判断 | ファーストビューに志望職種、強み、代表的な成果を配置する |

「分かりにくい」という回答があったことと、「何を配置すれば解決するか」は同じものではない。後者は、他の回答やポートフォリオの目的を合わせて作る仮説である。

### 5. 発見を課題文に変換した

単なる意見を、ユーザーの状況・困りごと・影響が分かる課題文に変換する。

例：

> 採用担当者が短時間で候補者の役割、強み、成果を把握したいとき、最初の画面から重要情報に到達しにくいため、候補者の実務能力を評価しづらい。

この課題文にすると、必要な情報や画面構成を検討できる。

### 6. 優先順位を決めた

優先順位は、回答数だけでなく、ユーザーへの影響と改善コストも合わせて考える。

| 課題 | 根拠 | ユーザーへの影響 | 改善コスト | 優先度 |
| --- | --- | --- | --- | --- |
| 何をしている人か分かりにくい | 3件中3件 | 評価の入口で迷う | 小〜中 | 高 |
| 成果や効果が分かりにくい | 評価項目・自由記述 | 実務能力を判断しにくい | 中 | 高 |
| 情報量・文章量が多い | 複数の自由記述 | 流し読みや離脱につながる | 中 | 中〜高 |
| アニメーションが閲覧を遅くする可能性 | 1件の指摘 | 閲覧速度が下がる | 中 | 中 |

今回は「影響が大きく、比較的改善しやすい」入口の情報不足を最優先の仮説とした。

### 7. 課題を設計要件へ変換した

| 課題 | 情報設計・機能設計への変換 |
| --- | --- |
| 何をしている人か分からない | ファーストビューに志望職種、強み、代表成果を表示する |
| 成果が分かりにくい | 作品ごとに成果・効果の項目を設ける |
| 担当範囲が不明 | 「自分の役割」「担当範囲」を明示する |
| 文章量が多い | 概要と詳細を分け、先に要点を見せる |
| 作品を探しにくい | 代表作品を上部に配置し、一覧から選べるようにする |
| 成果物へ移動しにくい | デモ、GitHub、詳細ページへのリンクを追加する |

## 現時点の仮説

> 採用側は、最初に「この人は何ができるのか」「代表的な成果は何か」を知りたい。しかし、現在のサイトではその情報に短時間で到達しにくい。

これは調査結果から得た有力な仮説であり、3件の回答だけで一般化した事実ではない。次の設計・検証で確かめる対象として扱う。

## 次の検証

- ファーストビューに職種・強み・代表成果を置いた案を作る
- 作品ページに役割、担当範囲、成果、リンクを追加する
- 変更前後で「何をしている人か」「成果が分かるか」を再評価してもらう
- 実際の採用担当者、デザイナー、未経験者など属性別に回答を比較する
