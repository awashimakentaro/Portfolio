# Designの本

対象はUI/UX・ビジュアル・体験設計を中心に紹介する制作。`books/design/<id>/`に保存する。共通の制作・表紙・検証・公開手順はSKILL.mdに従い、このレシピは質問と原稿の内容を担当する。

## ヒアリングの焦点

既存資料とintakeを読み、未回答の点だけ1問ずつ聞く。最初の例：「誰に、どんな体験や情報を届けたくてデザインしましたか？」

- 対象者・利用場面・当初の課題・目標は何か。何を一番伝えたいか。
- 誰に何を調査し、何が分かったか。本人の仮説・実際の回答・AIの仮想回答を分ける。
- 情報設計・フロー・ワイヤー・見た目・試作のうち実際に行った工程と本人の担当は何か。
- 比較した案と、採用した理由は何か。文字・余白・導線・演出の判断を具体例で聞く。
- 誰からどんな反応を得て、どこをどう変えたか。使える改善前後の画像はあるか。
- 確認できた結果・学び・残課題、使ったツールと用途。実装担当やAIの利用も正確に分ける。
- ワイヤーフレーム・FigJamのユーザー調査・プロトタイプ・完成デザインのうち、作った資料と見せたい箇所を確認する。既存URLを先に調べ、不足のリンクだけ聞く。全種類の提出を必須にしない。

## 紙面への対応

| 章／ページid | 掲載する内容 |
|---|---|
| 01 作品について／about | 正式名・体験の概要・対象者・動機・期間・担当、実画像と実在リンク |
| 02 課題・背景・目標／context | 調査の全体像の画像、課題・仮説・目標の短い説明、元FigJam |
| 03 制作プロセス／process | 工程ごとの実施内容・成果物・資料リンクを短く一覧化。本人の工程メモを基準にする |
| 04 検証・改善／review | フィードバックや試作検証、改善前後と理由 |
| 05 成果と効果／outcome | 確認できた成果。実施後の調査・A/Bテストの結果資料やFigJamがあれば掲載 |
| 06 使用技術・ツール／tools | 技術名を箇条書きで一覧表示。用途や選定理由は短く補足 |

完成画面の説明だけでなく「根拠→判断→変化」を文章や実画像で示す。仮説を調査結果に、自己評価をユーザーの評価に置き換えない。Figmaへアクセスできない場合は未確認と記録し、提供済み画像や回答で進める。目次はcontents、章が増減したら目次も更新する。

## Designの表示ルール（2026-11-08更新）

- 02は調査の全体像＋課題・目標。全体画像は資料の概要として見せ、細部は元資料へリンクする。集計の条件・仮想回答の注記を本文に残す。
- 03は画像を必須にせず、工程番号・工程名と「何をしたか→成果物」を短く並べる。Awashima Portfolioは本人のメモの01〜11工程を使い、複数の続きページに分けて同じ03ヘッダーを継承する。制作プロセスの画像は紙面から外し、元データは保持。01〜08の実施、09の公開済／利用者テスト予定、10の比較分析予定、11の整理中を区別し、計画書があるだけで完了にしない。他作品へ同じ11工程を機械的に強制しない。
- 制作過程や思考の詳細は、プロジェクト内の制作資料アーカイブへ集約してGitHub等の確認できるURLへリンクする。過去の仕様・学習メモ・AI用プロンプトは参考資料として区別する。移植・pushの依頼がある場合だけ公開対象を確認してpushし、元資料と無関係な未コミット変更を混ぜない。
- 05は実施済みの調査やA/Bテストがあれば条件・結果・改善と資料画像を掲載する。結果がまだなければ架空の画像・数値・空の成果カードを追加しない。本人が述べた学びと確認済みの成果を掲載し、結果資料は後で同じ章へ追加できる。
- 06は画像なし。Markdownの箇条書きで「React」「Three.js」等を並べる。必要なら用途別に小見出しで分け、1項目は技術名＋短い用途まで。長い説明文や未使用ツールは追加しない。
- 表示を磨くときも既存の書体・墨／生成り／銀灰を保ち、情報量・画像の大きさ・余白で主従をつける。カテゴリ専用レンダラーを新設することは必須ではない。

## 制作資料を本に載せる

Designでは次の資料も外部リンクで紹介できる。画像は本人が希望する章に限り掲載し、画像を外した03へ自動で戻さない。標準6章の関連する場所へ配置し、資料ごとの必須章や別の詳細ページは増やさない。

| 資料 | 主な掲載先 | 見せ方 |
|---|---|---|
| ユーザー調査・FigJam | 課題・背景・目標／検証・改善 | 調査の要点が読める範囲の画像と、判断にどうつながったかの解説、FigJamリンク |
| ワイヤーフレーム | 制作プロセス | 情報配置・導線が分かる画面と設計理由、Figmaの該当箇所へのリンク |
| プロトタイプ | 制作プロセス／検証・改善 | 操作の代表画面やフロー画像、試した内容の解説、「プロトタイプを操作する」リンク |
| UI・ビジュアルデザイン | 作品について／制作プロセス | 代表画面と表現・配色・余白などの判断、必要なら改善前後、Figmaリンク |

- まずintake.mdに「種類／元URL・ノードまたはローカルパス／見せたい内容／採用画像／掲載先ページid／確認状況」を記録する。希望・候補・取得済み・配置済みを区別し、未提供の資料を取得済みにしない。
- Figma・FigJamは利用可能な接続から対象ノードを読み取り、実物の画像を確認してから必要な範囲を書き出す。アクセス不可ならその理由を記録し、既存のローカル画像や提供資料で進める。URLやプロトタイプの開始点を推測しない。
- 掲載する実画像は各本のimages/へ保存する。例はwireframe-home.png、research-findings.png、prototype-flow.png、ui-history.png。外部の一時的な画像URLを本文へ直書きしない。資料の出典・取得日・切り出した範囲はintakeへ残す。
- 大きなFigJam全体図や縦長画面を縮めて文字を読めなくしない。意味の分かる部分を選び、短い説明を付ける。調査条件・注記を切り落として誤解させない。必要なら同じ章の続きページを追加し、ページ順と目次の移動先を維持する。
- 本文は単独行の`![説明](../images/ファイル名.png)`と`[資料を見る](実URL)`を使う。文章と画像のページはlayoutをimage-textにする。画像を主役にした資料専用ページは、Studioで画像を本文幅に表示できる既存のstatementも選べる。短い解説と合わせて収まりを確認し、本番3Dでの画像サイズは反映時に別途確認する。Figma等の資料リンクは本文に置き、Demo/GitHub専用のbook.ts.linksへ別のキーを追加しない。
- 本の中では静止画と解説を表示し、操作できるプロトタイプは外部リンクで開く。iframe・動画再生・FigJamの操作領域を紙面へ埋め込めるとは説明しない。掲載用のURLを閲覧できることと、第三者がログインなしで見られることは別に確認する。
- 個人情報を含む調査回答はそのまま公開用画像にしない。匿名化した要点を使い、実回答と仮想回答の区別を保つ。実際に動かしていないプロトタイプを検証済みと記載しない。
- プレビューでは画像内の文字がPC・小画面で読めるか、本文と画像が収まるか、リンクの表示名と行き先が合っているかを確認する。既存の公開境界は共通Skillに従う。
