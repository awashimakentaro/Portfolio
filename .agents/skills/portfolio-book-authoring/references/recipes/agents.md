# Agentsの本

対象はAIエージェント・Skill・作業支援の仕組み。共通の制作・表紙・検証・公開手順はSKILL.mdに従い、`books/agents/<id>/`へ保存する。

## 表紙

装丁は`public/book-covers/Agent-v2.png`。画像枠がない新しい原本を使い、画像未提供のAgentsにダミーのサムネイルや枠を足さない。名称と実在リンクだけで仕上げる。

## 主題

2026-11-07の最新回答で、本人は「制作プロセス・使用技術はAgentsには不要。作ったストーリーやどう変わったかを書けるようにしたい」と指定した。Apps・Designの6章に揃えず、作る前の困りごと、作ろうと思った理由、試行錯誤、使った後の変化を中心にする。以前決めた仕組み図・技術一覧を必須として復活させない。

## 基本構成

以下は最新要望を本へまとめるための編集上の標準。個々の作品に合わせて見出しやページ数は調整できる。

| 章／ページid | 掲載する内容 |
|---|---|
| 01 このエージェントについて／about | 誰が、何のために使うものか。短い概要と、提供された画像・リンク |
| 02 作ったきっかけ／context | 以前の困りごと、経験、目指した変化。制作動機が分かるストーリー |
| 03 作りながら気づいたこと／review | 最初の試み、うまくいかなかった点、考え直したこと、今の形につながった転機 |
| 04 使ってどう変わったか／outcome | 作業や学びの変化、できるようになったこと、実感、残る課題 |

最初の本文ページはタッチできる目次（id:contents）。1章1ページを優先しつつ、経緯を削りすぎず、必要なら同じ章の続きページに分ける。続きにも章ヘッダーを継承する。「制作プロセス」「使用技術・ツール」の独立章は作らない。

## ヒアリング

既存資料とintakeを読み、すでに答えたことを繰り返さず、答えやすい1問ずつ聞く。話し言葉や長い回答からCodexが原稿を整理する。

1. 作る前は、何に困っていたか。作ろうと思ったきっかけとなる経験は何か。
2. 最初はどう解決しようとし、何がうまくいかなかったか。
3. 何に気づき、考え方や使い方をどう見直したか。
4. 使う前と後で、実際に何が変わったか。代表的な出来事を1つ聞く。
5. 今も残る課題、次に良くしたいこと、掲載できる画像・実在リンクがあるか。

質問は全項目必須のフォームではない。既知の内容を先に原稿へ反映し、不足だけを聞く。仕組みの詳細・モデル・使用言語・技術選定を、必要な事実がない限り追加で聞き続けない。

## 原稿にするとき

- 本人の経験→困りごと→試したこと→気づき→変化のつながりが分かるように整える。本人が述べていない動機・成功談・失敗の原因を補わない。
- 「作りながら気づいたこと」は制作手順や技術解説の列挙にせず、本人の判断や転機を中心にする。読者に必要な仕組みの説明は短く添えられるが、図や実行ログは必須にしない。
- 変化は時間短縮・作業量・理解・負担・できるようになったこと等から、本人が確認できた内容を選ぶ。数値がなければ本人の定性的な実感でよい。未回答を未計測と断定せず、架空の削減率や評価を作らない。
- 本人の実感、特定の実例、一般ユーザーで検証した効果を区別する。AIが自動で理解を完了させる等、実装にない挙動を付け足さない。
- 個人的な挫折や会社の出来事は公開に適した範囲へ整文する。企業名・業務上の機密・第三者の評価や事情を推測しない。本人が詳しい公開を希望しているか不明なら、記録と公開候補の文章を分ける。
- Codexを基本にした作品という既存回答は制作記録に保持する。本文で必要なら一言触れられるが、技術一覧を掲載義務にしない。未提供のデモ・GitHub URLを作らない。

## 保存と再開

回答・出典・編集判断・省略・次の質問を各本のintake.mdへ保存する。古い技術説明・仕組み図・ページを既に持つ場合は参照資料として保持できるが、今回の希望と異なるページはbook.tsと目次から外す。公開用スナップショットの変更は共通Skillの明示的な反映手順に従う。
